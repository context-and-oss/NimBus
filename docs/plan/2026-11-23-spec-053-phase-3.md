# Spec 053 Phase 3: preview, classification filter, firing rules in Monitor and MCP

Date: 2026-11-23. Branch `feat/alert-rules-phase-3`. Spec: [Spec 053](../spec/053-alert-rules/spec.md)
(revision 7 records the design below).

## Context

Phases 0–2 (#434, #437, #438) shipped alert rules with four conditions. Phase 3 (spec §9) has
three parts, decided by the repo owner on 2026-11-23:

1. **Preview, exact kinds only.** Every kind shows its value now. Only `failure_occurrences` and
   `silence` get a 24-hour replay, because message history rebuilds them exactly. Backlog and
   blocked-session rules can't be replayed honestly: deletes leave no trace, and there is no past
   deferred count.
2. **A classification category filter** on backlog and occurrences rules. It applies only when
   Integration Intelligence can be read, and counts only failures an agent classified.
3. **Firing rules on the Monitor wall**, as a marker and a count, never a rule's name (a dashboard
   token sees every endpoint), and in the MCP worklist.

None of Phases 1–3 was released when this was built (v5.4.0 predates Phase 1), so
`IAlertSignalStore` gained members without a compatibility bridge.

## Design

- **Store.** `IAlertSignalStore` gains two members:
  - `CountMessagesPerMinute(endpointId, type, from, to, eventTypes, errorText)`: per-minute counts of
    one message type, for the replay.
  - `ListFailedAttempts(…, limit)`: the failed attempts' message and event ids, newest first, for
    the classification lookup.

  Both are on Cosmos DB, SQL Server and in-memory, with conformance tests.
- **Classifications.**
  - Insights' rule for when a saved classification counts became `ClassificationMatch` in
    `NimBus.Extensions.IntegrationIntelligence`. The counted result is live, names the same
    source, has a known category other than `unknown`, and has known guidance other than
    `Uncertain`. Insights and alert rules share it.
  - The evaluator reads classifications through `FailureClassificationReader.ReadLatestInBulkAsync`.
  - A backlog rule pages its failed events and checks their last attempts. An occurrences rule
    lists the attempts in its window.
  - Either looks at no more than 1,000 failures in one reading.
  - When classifications can't be read, or the ceiling is reached below the threshold, the reading
    is skipped. The state is left as it is (a 0 would resolve a rule that may still hold), the
    skip is logged, and it is counted on `nimbus.alert_rules.skipped{reason}`.
- **Condition reader.** The evaluator's condition reading moved to `AlertRuleConditionReader`, so the
  evaluator and the preview read a condition the same way.
- **Preview.** `POST /api/v1/endpoint/{endpointId}/alert-rules/preview` takes a draft condition and
  resolve time and saves nothing.
  - It returns the value now and, for occurrences and silence without categories, a replay. The
    replay is one `CountMessagesPerMinute` read over the last day plus the condition's lookback,
    stepped minute by minute through the evaluator's own `Apply`, on a scratch state, with no
    metrics.
  - The series is thinned to at most 288 points. The periods keep minute resolution.
  - Readers may preview. The form only offers it to Owners.
- **Monitor.** `MonitorFeedEndpoint.alertRuleFiring` is a boolean, null when unknown. The wall shows
  a "Rule firing" marker in the State cell and a "Rules firing" tile.
- **MCP.** `nimbus_get_worklist` gains `firingRules`: the rules firing on the caller's readable
  endpoints (catalog-scoped, so hidden ones stay out), longest firing first, at most 20. Each comes
  with its condition in words and an `open_web_ui` option to `/Endpoints/Details/{id}?tab=alerts`.
  The endpoint page now honours `?tab=`.

## Measurement (live Cosmos DB, 2026-11-23)

A temporary serverless account (`rg-nimbus-ru-probe`, swedencentral, MPN subscription), deleted the
same day. The `messages` container was provisioned as the Bicep does. The seed was the Phase 2 data
set: 200,000 messages over 24 hours on ten endpoints. Endpoint E00 has about 17,000 completed
messages and 1,950 failed attempts. Medians of three runs, through the gateway:

| Read | Case | Rows | RU |
|---|---|---|---|
| Per-minute counts, `ErrorResponse`, a day plus the window | about 2,000 failures | ~1,100 minutes | 166–168 |
| | error-text filter that matches nothing | 0 | 4.8–56.8 |
| Per-minute counts, `ResolutionResponse`, a day plus 60 min | about 17,000 completions | ~1,400 minutes | 304–312 |
| Failed attempts, newest first | 15 min | 7 | 4.1 |
| | 24 h, limit 1,001 | 1,001 | 51.6 |

What follows:

- **A preview costs 170–310 RU** on a busy endpoint. That is cheap on serverless (well under a
  hundredth of a cent), but on a provisioned account it competes with message processing. The
  Search policy's 120 a minute per user would allow about 37,000 RU a minute per user. So the
  preview got its own policy, `nimbus-alert-rule-preview`: 10 a minute per user
  (`RateLimiting:AlertRulePreview`), about 3,100 RU a minute at worst. The form never fetches on
  its own.
- **A category reading of 1,000 attempts costs about 50 RU**, plus the classification bulk read
  (about 1 RU per id on Cosmos DB). It runs once a minute per rule with categories, so the ceiling
  stays at 1,000.

## Deviations from the Phase 3 plan

- The Monitor feed carries only the per-endpoint flag. The wall counts the tile from the flags,
  so `MonitorFeedStatus` has no separate count.
- The preview's rate limit is its own policy, not Search: see the measurement.
- The preview endpoint previews a draft (`/alert-rules/preview`), not a saved rule
  (`/{ruleId}/preview` in spec §5.8 before revision 7), so the form can preview before saving.
- The endpoint page gained `?tab=`, so MCP can link to a rule's Alerts tab.
