# Spec 053 Phase 0: verify the facts, move the alert senders

Date: 2026-11-21. Branch `refactor/spec-053-phase-0`. Spec: [Spec 053](../spec/053-alert-rules/spec.md).

## Context

Spec 053 (alert rules, approved 2026-11-20) evaluates rules in the WebApp and notifies by mail and
webhook. Phase 0 prepares that without changing behaviour:

1. Settle the six facts in Spec 053 §14, so Phase 1 is designed on measured ground.
2. Move the mail and webhook senders out of `NimBus.Resolver`, which the WebApp can't reference
   (it is a Functions app), into a library both can use.

## Changes

1. `refactor(alerts)`: new `src/NimBus.Alerts` (net10.0, not packable; the Resolver and WebApp
   tools and images bundle project references), namespace `NimBus.Alerts`. Moved with `git mv`,
   with only the namespace changed: `AlertMailOptions`, `AlertSmtpOptions`, `IAlertMailSender`,
   `AlertMail`, `SmtpAlertMailSender`, `AlertMailComposer`, `AlertWebhookOptions`,
   `AlertWebhookBearerToken`, `IAlertWebhookSender`, `AlertWebhook`, both webhook exceptions,

   `IEndpointAlertNotifier`, `SubscriptionAlertNotifier` and `AddEndpointAlertNotifier` stay in the

### Fact 1: measurement

A serverless account in a temporary resource group (`rg-nimbus-ru-probe`, Sweden Central,
2026-11-21, deleted the same day). One endpoint container per data set, seeded through
`CosmosDbClient`'s own write methods (real documents, about 1 KB payloads, five event types, two
error texts). As many older failures as failures in the window, so the window filter has work to
do. The query: one endpoint, a 15-minute window, one bucket. Five runs after a warm-up; the
charge was identical across runs.

| Container | Failures in window | No filter | Event type (1 of 5) | Error text, matching half | Error text, no match |
|---|---|---|---|---|---|
| 10,000 events | 80 | 7.0 RU, 50–120 ms | 4.5 RU | 5.6 RU | 2.8 RU |
| 100,000 events | 873 | 42.6 RU, 94 ms | 12.4 RU | 26.9 RU | 2.8 RU |
| 20,000 events (outage) | 10,000 | 472.7 RU, 750 ms | 102.8 RU | 282.7 RU | 2.8 RU |

- A quiet endpoint costs 2.8 RU per evaluation whatever its size: about 121,000 RU per rule per
  month at one evaluation a minute, about $0.03 a month on serverless.
- The charge grows by about 0.047 RU per matching failure. During an outage, with 10,000 failures in
  the window, one rule costs about 470 RU a minute (8 RU/s), and 20 rules on that endpoint about
  160 RU/s. On a provisioned account of 400–1,000 RU/s that competes with message processing at
  the worst moment.
- Seeding cost about 19.4 RU per event written.

**Consequence for Phase 1** (Spec 053 revision 3, §5.3 and §7): a rule only needs to know whether
the count reaches its threshold, so the evaluator reads at most `threshold` failures with
`GetFailedEventsAcrossEndpoints` (an `UpdatedAt` window, page size = threshold) instead of
counting every failure. The charge is then bounded by the threshold, not by the backlog. The
threshold limit becomes 1–1,000, one page (`PaginationLimits.MaxPageSize`). That read was not
measured here; Phase 1 checks its charge on the first live account.
