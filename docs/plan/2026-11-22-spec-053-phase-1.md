# Spec 053 Phase 1: alert rules (`failure_backlog`)

Date: 2026-11-22. Branch `feat/alert-rules-phase-1`. Spec: [Spec 053](../spec/053-alert-rules/spec.md)
(revision 5 records the design changes below).

## Context

Spec 053 adds alert rules: an endpoint Owner defines "N or more events on this endpoint are failed
now", the WebApp evaluates it every minute, and the rule tells its own mail and webhook targets once
when it opens and once when it resolves. Phase 0 (#434) moved the senders to `NimBus.Alerts`;
#436 added the end-to-end endpoint-alert test. Phase 1 builds the feature, starting with the
measurement spec §7 asked for.

## Measurement (live Cosmos DB, 2026-11-22)

A serverless account in a temporary resource group (`rg-nimbus-ru-probe`, Sweden Central, deleted
the same day), seeded through `CosmosDbClient`'s own write methods. The backlog read is
`GetFailedEventsAcrossEndpoints(filter, [endpoint], null, maxItemCount: threshold)` with no date
bounds. Median of three runs after a warm-up; the charge was stable.

| Failures on the endpoint | Threshold 1 | 5 | 100 | 1,000 |
|---|---|---|---|---|
| 10 | 5.1 RU | 5.4 | 5.8 | 5.8 |
| 1,000 | 5.0 | 5.5 | 16.5 | 121.9 (447 ms) |
| 1,000, 4 KB error texts | 5.1 | 5.8 | 22.2 | 177.7 (862 ms) |
| 10,000 | 5.0 | 5.5 | 16.3 | 119.6 |

- An error-text filter that matches nothing costs 4.2 RU, except over long error texts, where
  Cosmos scans them: 58.7 RU for 1,000 failures with 4 KB texts.
- Phase 0's full count (`GetFailedEventHistogram`) cost 472.7 RU for 10,000 failures; the capped
  read costs about 5 RU at thresholds up to 5, whatever the backlog.

Rule bookkeeping, over 1,000 rule documents of about 2 KB (definition, state and 20 transitions):

| Operation | Charge |
|---|---|
| List due rules (cross-partition, no transitions), 900 rows | 56.7 RU, 130–270 ms |
| Point read of one rule | 1.0 RU |
| Conditional replace of one rule | 13.4 RU |

**Consequences (decided by the repo owner, 2026-11-22):**

1. **One evaluator lease per tick instead of per-rule claims.** Claiming and saving each rule every
   minute costs about 27 RU of writes per rule per minute whether anything changed: about 450 RU/s
   for 1,000 rules on a provisioned account, or $0.29 per rule per month on serverless. Instead,
   instances claim one lease a minute (like the heartbeat's `TryClaimHeartbeatSend`); the holder
   evaluates every enabled rule and writes a rule only when its state changes. Each write is
   conditional on the version read that tick, so an edit or a stale lease holder still can't
   overwrite. Rules show the evaluator's last completed tick, not a per-rule timestamp.
2. **Threshold 1–100.** Reads stay at about 30 RU or less; at 1,000 they cost 120–180 RU.

## Changes (one commit each)

1. `feat(storage)`: `IAlertRuleStore` (rules by `(endpointId, ruleId)`, logical version on every
   write, definition writes that can carry a state reset, conditional state writes, the evaluator
   lease) on Cosmos DB (`alertrules` container, `/endpointId`), SQL Server
   (`0029_AlertRules.sql`) and in-memory, with a conformance suite.
2. `feat(alerts)`: rule notices in `NimBus.Alerts`: a signed version-2 webhook body with
   `X-NimBus-Notice` and a secret derived per rule target, and a mail naming the rule, the endpoint
   and the condition in words. Subscription alerts unchanged.
3. `feat(webapp)`: the evaluator (`Services/AlertRules`) and the API (`AlertRulesImplementation`,
   `/api/v1/endpoint/{endpointId}/alert-rules`, `/api/v1/alert-rules/firing`), audited.
4. `feat(deploy)`: the WebApp gets the alert mail settings and bearer-token prefixes (Bicep, `nb`,
   both AppHosts).
5. `feat(webapp)`: the Rules section on the Alerts tab and the Firing marker on the endpoint list.
6. `docs` and the end-to-end rule test.

## Deviations from the Phase 1 plan

- The Resolver's settings reader was not moved to `NimBus.Alerts`; it would have needed the
  configuration binder there for about ten lines. The WebApp binds the same option types itself.
- The evaluator's last completed tick lives in the rule store's lease, not in a `ServiceHealth`
  row.
