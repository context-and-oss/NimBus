# Spec 053 Phase 2: `failure_occurrences`, `blocked_session`, `silence`

Date: 2026-11-23. Branch `feat/alert-rules-phase-2`. Spec: [Spec 053](../spec/053-alert-rules/spec.md)
(revision 6 records the design below).

## Context

Phase 1 (#437) shipped alert rules with one condition, the failure backlog: the events failed now.
Phase 2 adds the three conditions the backlog can't express:

- **failure_occurrences**: N or more failed attempts on the endpoint in the last W minutes, counted
  from message history even if the events were resolved later (spikes).
- **blocked_session**: the oldest Failed or handed-off event holding a session has not changed for
  T minutes, **or** N or more events are deferred on the endpoint. The repo owner chose both; either
  fires the rule.
- **silence**: no message on the endpoint completed (a `ResolutionResponse`) for T minutes. The repo
  owner chose this meaning: failures are not activity.

No existing store read fits cheaply. `GetEndpointMetrics` and `GetFailedMessageInsights` read every
endpoint's messages in the window (on Cosmos DB a fan-out over the shared `messages` container,
uncapped), and nothing returns the oldest blocking event. So Phase 2 adds a narrow optional store
capability and measured it first.

## Design

- `IAlertSignalStore` (`NimBus.MessageStore.Abstractions`), an optional capability like
  `IAlertRuleStore` (ADR-018). Adding members to `IMetricsStore` would break external providers, and
  the OpenTelemetry decorator wraps only `IMessageTrackingStore`.
  - `CountFailedAttempts(endpointId, fromUtc, toUtc, eventTypes?, errorTextContains?, cap)`: stored
    `ErrorResponse` messages (dead-letters included) for exactly that endpoint, in [from, to), at most
    `cap`.
  - `GetOldestBlockingEvent(endpointId)`: the oldest non-deleted Failed, or Pending with sub-status
    Handoff, event. DeadLettered doesn't block.
  - `HasCompletedMessageSince(endpointId, sinceUtc)`: any `ResolutionResponse` since then.
  - The deferred count reuses `IMessageTrackingStore.DownloadEndpointStateCount`.
- `AlertRuleCondition` gains `WindowMinutes`, `Minutes` and `DeferredThreshold`. The API keeps only
  the fields the kind uses.
- The evaluator reads each condition as (holds, value, volatile). A duration (minutes blocked)
  changes every minute, so it is recorded only with a transition: a rule is not written every
  minute while the age grows. A count keeps Phase 1's behaviour. Rules whose kind the provider
  can't read are skipped and logged, and the API refuses to create them (`availableKinds`).
- Notices: `conditionKind` is added to the version-2 webhook body. The condition text, the value
  label, the resolve reason and the link follow the kind (occurrences → the Failed view for the
  window's period; blocked session → the endpoint's Failed/Pending/Deferred view; silence → the
  endpoint).

## Measurement (live Cosmos DB, 2026-11-23)

A temporary serverless account (`rg-nimbus-ru-probe`, swedencentral, MPN subscription), deleted the
same day. The `messages` container was created as `deploy/bicep/templates/cosmosDB.bicep` provisions
it (partition `/eventId`, 90-day TTL, the same indexing policy). Seed: 200,000 messages over the last
24 hours across ten endpoints (20,000 each: 85 % `ResolutionResponse`, 10 % `ErrorResponse` of which
a quarter carry 2 KB error texts, 5 % `EventRequest`); `E09` has no message in the last two hours.
Writing them cost 3.6 M RU (18 RU a message). Blocked sessions: endpoint containers with 1,000 and
5,000 events. Median of three runs after a warm-up, through the gateway:

| Read | Case | RU |
|---|---|---|
| `CountFailedAttempts` | 15 min window, cap 1–100 (6 matches), any filter | 3.7–5.1 |
| | 24 h window (2,000 failures), cap 1 or 5, no filter or event type | 4.2–4.6 |
| | 24 h window, cap 100 | 8.0–10.3 |
| | 24 h window, error text that matches nothing (scans the 2,000 error texts) | 59.3 |
| | an endpoint with no failures in the window | 3.6 |
| `HasCompletedMessageSince` | busy endpoint, 15 min or 24 h | 3.8–4.2 |
| | silent endpoint, 15 or 60 min | 3.3–5.6 |
| `GetOldestBlockingEvent` | 1,000 or 5,000 events on the endpoint | 3.4–3.5 |
| `DownloadEndpointStateCount` (deferred count) | 1,000 events | 8.9 |
| | 5,000 events | 49.5 |

What follows:

- Every new read costs about 4 RU in the common case, like the backlog read. The window and the cap
  barely matter, because the reads seek the endpoint and type and stop at the cap.
- The expensive case is an error-text filter that matches nothing over a long window: Cosmos scans
  every failed attempt's error text in the window, about 0.03 RU each. A 24-hour window with 2,000
  failures costs 59 RU, the same order as Phase 1's error-text backlog read. The window limit stays
  at 24 hours (1,440 minutes); at 20,000 failures a day such a rule would cost about 600 RU a minute,
  which the docs and the spec name as the case to avoid.
- The deferred count is the existing endpoint-wide state count, about 0.01 RU per event on the
  endpoint. The evaluator reads it once per endpoint per tick, so several blocked-session rules on
  one endpoint share it (`9d1985f7`).
- Limits: threshold 1–100 (unchanged), window 5–1,440 minutes, blocked minutes 1–1,440, silence
  5–1,440 minutes, deferred threshold 1–1,000.

Two problems with the measurement itself, recorded so the numbers can be trusted:

- The first seed shared one `System.Random` across 64 concurrent writes. Once corrupted it returned
  0, so 99 % of the messages were successes at the same time. The data was dropped and reseeded with
  `Random.Shared`.
- Direct-mode connections stopped completing their TLS handshake after a network change, so the probe
  ran through the gateway. Charges are the same in both modes.

Found on the way, not changed here: the bicep's excluded path `/message/messageContent/*` is
lower-case, but documents store `MessageContent`. Cosmos index paths are case-sensitive, so message
content is probably indexed in every deployment.

## Deviations from the Phase 2 plan

- The blocked-session value is minutes blocked; a rule that watches only the deferred count reports
  0 minutes, shown as "–".
- Disabling or enabling a rule in the UI used to rebuild it as a backlog rule; fixed with the kind
  selector, with a regression test.
- The measurement used 200,000 messages, not 1 M: the costs depend on the matches for one endpoint
  in the window, not on the container's size, and the 200,000-message run already shows the scan.
