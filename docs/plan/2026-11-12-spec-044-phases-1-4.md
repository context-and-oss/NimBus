# Plan: Spec 044 — Agent-first NimBus, phases 1 to 4

Spec: [docs/spec/044-agent-first/spec.md](../spec/044-agent-first/spec.md) (revision 3). Baseline:
master `bc0667f9`; the latest release is v4.11.0. Branch for this plan: `docs/spec-044-plan`.

Phase 1 has shipped to master (#361) and has its own plan,
[2026-11-11-spec-044-phase1-agent-recording.md](2026-11-11-spec-044-phase1-agent-recording.md).
This plan records what is left of it, then plans Phases 2 to 4 in the detail the spec leaves to
"its own plan". Every code claim below was checked against `bc0667f9`.

| Phase | Goal | State | Delivery |
|---|---|---|---|
| 1 Understand | Agents read evidence and record classifications | Merged in #361, not yet released | Follow-ups F1–F4 below, then the next 4.x minor |
| 2 Retry unattended | Operation journal; workloads resubmit within a budget and a cap | Planned | One PR, then a 4.x minor |

## Delivery rules

- One PR per phase, branched from master after the previous phase merges, with one commit per
  part. No stacked PRs. A fix that stands on its own (F1, P3.0) goes in its own PR first.
- Every phase leaves master releasable and is additive in 4.x. Nothing deprecated in Phase 1 is
  removed before v5.0.0.
- Storage changes are implemented on SQL Server, Cosmos DB and in-memory, with a conformance
  suite. Members added to `IMessageTrackingStore` are forwarded by
  `InstrumentingMessageTrackingStoreDecorator`. A new store is a separate optional interface
  (ADR-018), resolved optionally by the WebApp, so that external providers keep compiling.
- SQL migrations are numbered at implementation time. The latest on master is `0025`, and other
  open branches may also claim `0026`.
- Verification for every phase:
  - `dotnet build src/NimBus.slnx -c Release`, with the newest 10.0.4xx SDK pinned through a
    temporary `global.json`, then `dotnet test -c Release --no-build`, run only if the build
    succeeded.
  - `npm --prefix src/NimBus.WebApp/ClientApp run test:ci` and `run build`.
  - `npm --prefix website run build` whenever `docs/` changes.
  - Live SQL and Cosmos conformance tests run in CI. Locally they run when the containers are up;
    otherwise the PR reports them as skipped.
  - A screenshot in the PR whenever the Web UI changes.

## Decisions this plan needs

Each decision either resolves a conflict between the spec and the code, or fills in something the
spec leaves open. Each is marked **(amends the spec)** or **(fills a gap)**. When one is agreed,
the spec is amended in the same PR as the phase that needs it.

| # | Topic | Proposal | Why |
|---|---|---|---|
| D1 | Receiver-side receipts (§7.1) **(amends the spec)** | Change no Core, Resolver or transport code. The Manager publishes each journaled command with a stable `MessageId`, the operation id. The Resolver's stored copy of that message serves as the receipt, and the response whose `ParentMessageId` equals it serves as the outcome. The subscriber's inbox, where enabled, already skips a redelivered resubmission with a recorded `MessageId`. NimBus never republishes a command automatically. | §12 rules out Core, Resolver and transport changes. Today `ManagerClient.Resubmit` sets no `MessageId` and the broker assigns one, so the WebApp cannot find its own command later. Topic duplicate detection must stay off (`MessageContext.cs`, `ServiceBusTopologyProvisioner.cs`). |
| D2 | Budget per agent (§7.3) **(fills a gap)** | An agent is a workload client id (`azp`, else `appid`) within its tenant. The budget counts its journaled resubmits over a rolling 24 hours: default 20, Owner range 0–500. It is durable, read from the journal, and applies even when rate limiting is off. The per-minute change limit still applies on top. The budget never raises it. | The change limiter (`OperatorMutationLimiter`) is per process, resets on restart and is off when `RateLimiting:Enabled=false`. So "at or below the change limit" cannot be the only bound. |
| D3 | Stack traces (§8.2) **(amends the spec)** | Add an opt-in to Core: a subscriber setting, off by default, that stores the reported exception's `StackTrace` (frames only) in `ErrorContent.ExceptionStackTrace`, cut at 8,000 characters. Amend §12 to allow it. The other option is to drop §8.2, leaving agents with only the exception type and message to find the code by. | `ResponseService.CreateErrorContent` sets `ExceptionStackTrace` and `ExceptionSource` to null, so §4's claim that the trace "is stored" is wrong for current adapters. |
| D4 | Linking failures to a report (§8.3) **(amends the spec)** | Add a new read tool, `nimbus_find_reports`, backed by a new store member that lists an endpoint's reports by ticket. Do not add `reported` and `ticketId` filters to `EventFilter`. | Reports live in their own table or container (`EventReports`, `eventreports`). On Cosmos they cannot be joined to the per-endpoint event containers, and "not reported" would need an anti-join that breaks continuation paging. Every message row already carries `isReported` and `ticketId`. |
| D5 | Endpoint metadata editor (§8.1) **(fills a gap)** | Mount the existing, unmounted `MetadataTab` as an endpoint-details tab and extend it. Store a ticket-link template per endpoint (https, must contain `{ticketId}`) as the tracker address. It overrides the site's existing `TicketLinkTemplate`, which settles §14 Q4. | `metadata-tab.tsx` is imported nowhere. The endpoint-details tabs are Messages, Event Types, Alerts and Audit. A site-wide `TicketLinkTemplate` already exists. |
| D6 | Data-quality exit case (§9) **(amends the spec)** | Use the `contract_schema` reason for "report data quality": the source sent `CountryCode` "Denmark" where ISO alpha-2 is expected. `missing_reference_data` stays a hand-to-person or retry-later case. | The catalog says of `missing_reference_data`: "Replaying after the reference exists succeeds." An honest agent answers a low change-required likelihood, which composes `Investigate`, and the failure goes to a person. |
| D7 | Unattended prompt text **(fills a gap)** | `handle-failures` gains an optional `unattended` argument (default false). It changes only the text: no confirmation questions, retries within the budget the capabilities report, and a recorded hand-over in place of a question. Enforcement stays on the server (roles, switches, budget, cap). | The prompt and rule 2 of the server instructions both require "the user's explicit yes" (`OperatorPrompts.cs`, `OperatorInstructions.cs`). In LocalDevelopment mode the caller is a person, not a workload, so the server cannot choose the text from the caller type. |
| D8 | Runner (§9) **(fills a gap)** | A .NET console sample. It gets the token, checks the capabilities and fetches the prompt over MCP, then hands the prompt to a headless coding-agent CLI. Claude Code (`claude -p`) is the reference; the command is configurable. | The model and the coding agent belong to the customer (principle 1). Claude Code has no tool for fetching an MCP prompt, so the runner fetches it. The repository already uses the MCP .NET client in tests (`McpTestHost.cs`). |

- `FailureClassificationRecorder` stores `RequestedBy = _host.CurrentActor ?? "unknown"`.

  this.

  `Name` in `McpAccessSettings.Clients`, else `app:{azp|appid}`.
- Regression tests: a workload token without `name` records a classification and writes an audit
  row, and both carry the client name.

### Part 2.2 — the operation journal store

**Contract** (`src/NimBus.MessageStore.Abstractions`): `IOperatorOperationStore`, with the record
`OperatorOperation`:

| Field | Meaning |
|---|---|
| `OperationId` | GUID, `N` format; also the command's `MessageId` |
| `TenantId`, `Caller`, `ClientId`, `IsWorkload`, `ActorName` | Who asked (caller = `oid ?? sub`, as `OperatorActionTokens.Identify`) |
| `IdempotencyKey`, `ArgumentsHash` | SHA-256 over action, endpoint, event, message version and reason |
| `Action` | `Resubmit` or `Skip` |
| `EndpointId`, `EventId`, `SessionId`, `SourceMessageId`, `MessageVersion` | What it acts on |
| `Reason` | As audited |
| `Status` | `Accepted` → `Claimed` → `Publishing` → `Dispatched` → `Succeeded` / `Failed`; also `NotSent`, `OutcomeUnknown`, `Refused` |
| `ObservedStatus`, `EvidenceMessageId`, `ObservedAtUtc` | The response read from the Resolver's history |
| `LeaseOwner`, `LeaseUntilUtc` | Reconciler lease |
| `CreatedAtUtc`, `UpdatedAtUtc`, `ExpiresAtUtc` | Retention: 30 days |
| `Version` | Optimistic concurrency (SQL `rowversion`, Cosmos `_etag`) |

**Members:**
- `TryCreateAsync(op)` returns `Created` or `Existing(op)`, unique on
  `(TenantId, Caller, IdempotencyKey)`.
- `GetAsync(operationId)`.
- `FindByIdempotencyKeyAsync(tenant, caller, key)`.
- `TryUpdateAsync(op, expectedVersion)`.
- `TryAcquireLeaseAsync(operationId, owner, until)`.
- `ListDueAsync(statuses, updatedBefore, limit)`.
- `CountAsync(OperatorOperationCount query)`, which serves both the budget (client, window) and
  the cap (endpoint, event, workload, statuses).
- `PurgeExpiredAsync(now, limit)`.

**Providers:**
- **SQL:** migration `00NN_OperatorOperations.sql`.
  - Primary key `OperationId`.
  - Unique index `(TenantId, Caller, IdempotencyKey)`.
  - Indexes `(EndpointId, EventId)`, `(ClientId, CreatedAtUtc)` and `(Status, UpdatedAtUtc)`.
  - Add the table to `SqlServerSchemaInitializer.RequiredTables` and to the test reset list in
    `SqlServerStoreTestHarness`.
- **Cosmos:** container `operatoroperations`, partition key `/id`.
  - The document id is the idempotency id, a SHA-256 of tenant, caller and key, so creation is
    conditional on a point key. `OperationId` is stored as a property and also has a lookup
    document. As an alternative, `GetAsync` can run a cross-partition query over this small,
    TTL-bounded container; choose by RU cost when implementing.
  - Item TTL is 30 days.
  - Add the container to `CosmosContainerDefaults.ReservedContainerIds` and to `sharedContainers`
    in `cosmosDB.bicep`. `CosmosBicepContainerSyncTests` enforces both.
- **In-memory:** `InMemoryMessageStore`.
- **Registration:** by casting the aggregate store, as the dashboard token store does
  (`SqlServerMessageStoreBuilderExtensions`, the Cosmos builder).
- **Conformance:** `src/NimBus.Testing/Conformance/OperatorOperationStoreConformanceTests.cs`,
  with subclasses in the three `*OtherStoreConformanceTests.cs` files. It covers:
  - idempotent create, and the same key with different arguments;
  - CAS conflicts and lease exclusivity;
  - both count queries, and expiry and purge;
  - DateTimes compared by ticks.

### Part 2.3 — the coordinator writes through the journal

`OperatorCommandCoordinator.RunAsync` today runs claim (`TryArchiveUnresolvedEvent`), then the
required audit, then publish. When publish throws it releases the claim, so a retry with the same
key can publish twice. The class doc names the crash gap between claim and publish.

The MCP resubmit and skip path, delegated callers included, becomes:
1. **Authenticate and authorize** as today: scope, readable endpoint, change policy.
2. **Look up `(tenant, caller, idempotencyKey)`.** The same arguments return the existing
   operation and run nothing; this happens before the token's expiry or message state is checked.
   Different arguments answer `[InvalidArgument]`.
3. **Check** the token binding, the limiter and the state guard, as today.
4. **`TryCreateAsync`** with status `Accepted`. Workloads are then counted, the new entry included
   (Part 2.5). Over budget or over the cap, the entry becomes `Refused` and the call answers
   `[ActionNotAllowed]`. Counting after the create makes two concurrent calls refuse each other,
   not both pass.
5. **Claim** (`Claimed`), then the **audit**, whose data gains `operationId`, then **`Publishing`**,
   then publish with `commandMessageId = OperationId`, then **`Dispatched`**.
6. **Publish throws:** release the claim as today and mark `OutcomeUnknown`. Never republish.

**`OperatorOperationReconciler`:**
- A hosted service registered as `AddSingleton<IHostedService>(factory)`. A second
  `AddHostedService` of the same class is silently dropped.
- Every 30 s it leases up to 50 due operations:
  - `Accepted` or `Claimed` past its lease: nothing was published. Restore the row with
    `TryRestoreArchivedEvent`, audit `CommandNotSent` and mark `NotSent`.
  - `Publishing` past its lease, or `OutcomeUnknown`: look for the command with
    `GetMessage(eventId, operationId)`. If it is found, mark `Dispatched`. If it is still absent
    after a grace period (default 60 min, because the Resolver can lag), restore the row if it is
    still archived and leave the operation `OutcomeUnknown` for a person.
  - `Dispatched`: in `GetEventHistory(eventId)`, find the response whose `ParentMessageId` equals
    the operation id:
    - `ResolutionResponse` → `Succeeded`.
    - A `SkipResponse` → `Succeeded`: the skip itself, or the inbox's "DuplicateDetected".
    - `ErrorResponse` or `UnsupportedResponse` → `Failed`.
    - `PendingHandoffResponse` → stays `Dispatched`, with `ObservedStatus = PendingHandoff`.
  - It purges expired operations.
- **Without an `IOperatorOperationStore`:** MCP resubmit and skip keep the Phase 2a behaviour,
  `nimbus_get_operation` is not listed, and unattended resubmit is unavailable.
- **Out of scope:** the Web UI and bulk admin paths stay off the journal. `AdminService`'s bulk
  resubmit bypasses the coordinator today, and moving it is separate work.

**Tests** (`OperatorCommandCoordinatorTests`, plus new reconciler tests):
- a crash after claim, after audit and after publish (fault-injecting fakes);
- a lost acknowledgement, and a retry with the same key after `OutcomeUnknown` that publishes
  nothing;
- the outcome correlated from the history, the Resolver lag window, and a lease held by another
  replica.

### Part 2.4 — MCP tools

- **`nimbus_resubmit_message` and `nimbus_skip_message`:**
  - The results gain `operationId` and `status`.
  - Annotations become `Idempotent = true`.
  - The descriptions say to poll `nimbus_get_operation`.
- **`nimbus_get_operation`** (read):
  - Argument: `operationId`.
  - Needs Endpoint Reader on the operation's endpoint, a visible endpoint and the same tenant.
    There is no lookup across tenants.
  - Returns the status, action, endpoint and event, the times, `observedStatus`,
    `evidenceMessageId`, `safeToResubmitAutomatically` (always false for `OutcomeUnknown`) and a
    `nextAction` sentence.
  - It reconciles on read with the same logic as the reconciler, so a result never lags the
    history.
- **`nimbus_get_capabilities`:** `CallerInfo` gains `IsWorkload`. A new `Unattended` block gives
  the budget (limit, used, window) and the per-message cap, or null for delegated callers.
- **Tests:** the existing `OperatorActionToolsTests` pass unchanged on the in-memory journal. New
  tests cover operation lookup, cross-endpoint refusal, the hidden-endpoint refusal and
  reconcile-on-read.

### Part 2.5 — workloads, budget and cap

Follow the Phase 1 pattern for `AllowWorkloadClassification`, which touched:
- `McpAccessSettings`;
- `McpAccessPolicy`, `OperatorActionAccess.HoldsScope` and its refusal text;
- `McpOperatorPermissions`;
- `McpAccessRules.Changes`, `McpAccessApiMapper` and `api-spec.yaml`;
- `mcp-access-model.ts`, `mcp-access-settings.tsx` and its test;
- `EndpointMetadataStoreConformanceTests`;
- `AgentClassificationToolsTests`;
- `docs/mcp-server.md`.

Changes:
- **App role:** `McpOperatorPermissions.ResubmitRole = "Nimbus.Resubmit"`. There is no role for
  skip (decision 7).
- **Settings** (`McpAccessSettings`, one JSON document, no migration):
  - `AllowWorkloadResubmit` (default false);
  - `WorkloadResubmitsPerDay` (default 20, range 0–500);
  - `WorkloadResubmitsPerMessage` (default 2, range 1–5).
  - Switching on and raising either number count as widening in `McpAccessRules.Changes`.
- **Policy and access:**
  - `AllowsWorkloadResubmit = AllowWorkloads && AllowWorkloadResubmit && journal present`.
  - `HoldsScope(Resubmit)` accepts a workload holding the role while the policy allows it.
    Contributor still comes from the NimBus ACL (the workload's `oid`).
- **Budget (D2):** count the client's `Resubmit` operations in the last 24 hours, every status
  except `NotSent` and `Refused`.
- **Cap:** count `Resubmit` operations by workloads on `(endpoint, event)` whose status is not
  `Succeeded`, `NotSent` or `Refused`, within retention, across agents. At the cap, answer
  `[ActionNotAllowed]` "agents have resubmitted this message N times without success; hand it to a
  person".
- **Wording that says workloads cannot change messages:** `OperatorInstructions.cs` rule 2,
  `mcp-access-settings.tsx`, `mcp-access-model.ts` and `OperatorActionAccess`. Update it, and the
  assertion in `AgentClassificationToolsTests` that a workload never sees "resubmit".
- **Tests:**
  - A workload with the role and the switch resubmits.
  - It is refused without the role, with the switch off, for skip, over budget and at the cap.
  - The budget and the cap hold across a host restart, because they come from the journal.
  - Two concurrent calls at the boundary both refuse.

### Part 2.6 — prompt, instructions and docs

- **`handle-failures`** gains `unattended` (D7). In unattended text the retry step runs:
  1. `nimbus_prepare_action`, then `nimbus_resubmit_message`;
  2. poll `nimbus_get_operation` until it reaches a terminal status, at most 5 times about 15 s

### P3.0 — prerequisite: the metadata write path (its own PR)

- **What's wrong with `PostMetadataEndpointAsync` today:**
  - It builds a fresh `EndpointMetadata`. On SQL that nulls `IsHeartbeatEnabled`,
    `EndpointHeartbeatStatus` and `SubscriptionStatus`. On Cosmos the whole-document upsert also
    drops `Heartbeats`.
  - It throws when `technicalContacts` is null.
  - It writes no audit row.
  - It checks no lengths, although the SQL columns are `NVARCHAR(200/400)`.
  - It has no tests.
- **Fix:** rewrite it as a read-modify-write of the stored metadata, keyed on the route's
  endpoint. Validate the lengths, append the audit type `UpdateEndpointMetadata` to the enum (and
  update `AdminCleanupAuditTests`, `api-spec.yaml` and `docs/webapp-rest-api.md`), and add tests.
- **Why first:** Phase 3 makes this record steer where agents file issues and pull requests, so it
  must be fixed beforehand.

- **`nimbus_get_endpoint`:**
  - It returns `Ownership` (owner, team, email, technical contacts, source system, repository

### Part 3.2 — stack traces (D3)

- **Core, opt-in:** a subscriber setting, off by default. When it is on, `CreateErrorContent`
  stores `reported.StackTrace`, cut at 8,000 characters. The plan names the option when D3 is
  agreed. Docs: `building-adapters.md`, which today says the trace is not stored.
- **Evidence:**
  - A new scrub path. `IntelligenceDataRedactor.ScrubText` returns null for any text matching
    `ExceptionDumpPattern`, so it would drop every trace.
  - The new path keeps the frames, cuts file paths down to the file name, and applies the secret
    patterns and the sensitive-value masker.
  - The trace never enters `OutboundFailureState`, so the deprecated provider never sees one.
- **Owner switch:** `Data.IncludeStackTrace` in `FailureClassificationDataOptions` and
  `IntelligenceAdminSettings`. It is not `[JsonRequired]`. The class disallows unmapped members,
  so an older instance rejects a save that carries the field during a rolling deploy; the release
  note says so. The **Failure evidence** card gets a toggle, and the side-panel text "No … stack
  traces" changes.
- **Tool:** `nimbus_get_failure_evidence` gains `includeStackTrace`. No other tool returns traces,
  and `OperatorMessageToolsTests`' no-trace assertion for `nimbus_get_message` stays. Update
  `docs/mcp-server.md`, which says "results never contain stack traces".

### Part 3.3 — linking failures to a report (D4)

- **Store:** `FindEventReports(endpointId, ticketId?, continuationToken, max)` on
  `IMessageTrackingStore`.
  - It is implemented in all three providers, forwarded by the decorator and covered in
    `MessageTrackingStoreConformanceTests`.
  - SQL adds an index `(EndpointId, TicketId)`. Cosmos queries the `eventreports` partition
    `/EndpointId`.
  - Test fakes that implement the interface need the member, `FakeCosmosDbClient` included.
- **`nimbus_find_reports`** (read):
  - It lists an endpoint's reported events, optionally for one ticket. Each row carries the
    ticket, the reporting time and person, the current status, and the normalized error pattern
    (`ErrorPatternNormalizer`, as Insights uses).
  - The agent looks for a matching pattern before it files anything.
  - Pages hold at most 50 rows. Each row is read with `GetEvent`, because `GetEventsByIds` needs
    stored `{EventId}_{SessionId}` ids on Cosmos and a report has no session id.
- **`nimbus_set_message_reported`:**
  - It accepts `eventIds` (1–50, one endpoint), or the existing `eventId`.
  - Each event is audited and returns its own result.
  - A call takes one limiter permit.
- **Workloads:** the `Nimbus.Annotate` app role and an `AllowWorkloadAnnotation` switch, following
  the Part 2.5 pattern.

### Part 3.4 — resubmit by ticket

- **Prepare:** `nimbus_prepare_action` accepts `ticketId`, in place of `eventId` and
  `messageVersion`.
  - It selects the endpoint's reported events with that ticket that are Failed or DeadLettered,
    at most 50.
  - It stores a prepared batch with each member's version in the journal (status `Prepared`,
    expiring in 2 minutes), so the token carries only the batch id.
  - The preview gives the count, the sessions affected and any members that are not eligible.
- **Execute:**
  - Each member runs through Part 2.3 as its own operation: its own state guard, budget and cap.
  - Results come back per message, and stale members report `[StaleMessage]` without stopping the
    rest.
  - The pattern to copy is the bulk skip in `AdminService.Purge.cs`, which loops through the
    coordinator.
- **Tests:** a mixed batch (eligible, stale, at the cap), a budget that runs out partway through,
  and a replay with the same key.

### Part 3.5 — Insights by fault origin (§8.5)

- **Perspective:** add `faultOrigin` to the `InsightsPerspective` enum.

## Phase 4 — run unattended (§9)

### Part 4.1 — the reference runner (D8)

`samples/FailureAgent/FailureAgent.Runner`, a .NET 10 console in `src/NimBus.slnx` under
`/Samples/FailureAgent`, so that CI builds it, with `tests/FailureAgent.Runner.Tests` (MSTest).

**Steps:**
1. **Read the configuration** (`FailureAgent:*`):
   - `McpUrl`, `Authentication` (`Entra` | `LocalDevelopment`) and `Scope`
     (`api://<mcp-app>/.default`);
   - `EndpointId?` and `Period`;
   - `WorkingDirectory` and `AgentCommand` (default `claude`);
   - `MaxBudgetUsd` and `Model?`.
2. **Get an app-only token** with `Azure.Identity`: workload identity federation in CI, managed
   identity in Azure, a client secret as a last resort. In LocalDevelopment mode, use no token.
3. **Connect with the MCP .NET client and check `nimbus_get_capabilities`:**
   - the caller is a workload (Entra mode);
   - `permittedActions` include `classify`;
   - the `Unattended` block exists.
   - Otherwise stop with a clear exit code.
4. **Fetch the prompt:** `prompts/get handle-failures` with `unattended=true`, `endpointId` and
   `period`.
5. **Write a temporary MCP config** (http, the URL, an `Authorization` header) readable only by
   the runner.
6. **Run the agent:**
   `claude -p --strict-mcp-config --mcp-config <file> --permission-mode dontAsk --allowedTools
   <NimBus tools, git, gh, Read, Edit, Write> --disallowedTools mcp__nimbus__nimbus_skip_message
   --output-format json --max-budget-usd <n> --no-session-persistence [--model <m>]`, with the
   prompt on stdin. These flags were checked against Claude Code 2.1.322.
7. **Summarize** the JSON result: outcomes per failure and the cost. A failed run exits non-zero.

Tokens last 60–90 minutes, so the runner refuses a configured run time longer than the token's
remaining lifetime.

**Templates in the sample** (copied by the customer; not active in this repository):

  - a scheduled workflow;
  - `azure/login` with OIDC, for the runner's federated credential;
  - a repository token from a GitHub App installation, scoped to the adapters' repositories with

### Part 4.3 — exit on CrmErpDemo

A script, `samples/FailureAgent/scripts/crmerp-exit.ps1`, run by hand. It is not part of the
nightly e2e: a real model costs money and does not give the same answer every time, and a retried
test fails CI.

**Seed the failures:**
1. Create one failure per reason, each on its own account so that each blocks only its own
   session: `transient_dependency`, `contract_schema` (D6) and `authentication_configuration`.
   Use `PUT /api/admin/error-mode` with the reason, then create the account and wait for Failed.
2. Turn error mode off. Every handler throws while it is on, so a retry can only succeed after
   this.

**Run the runner** in LocalDevelopment mode on the same host. `/mcp` admits loopback calls only,
so a container resource would get 403. The tracker for the run is a folder: each report is a file
whose name is the ticket id, passed through `--append-system-prompt`.

**Expected, read back over MCP:**
- the transient failure is Completed after one operation;
- `contract_schema` is classified `source_data` with `ChangeLikelyRequired`, and marked reported
  with a ticket;
- the credentials failure is classified `configuration` and left Failed, with a rationale.

**Then the Azure pilot:** the same run with a workload identity against the Azure CrmErpDemo
deployment. This proves the app roles, the switches and the budget, which LocalDevelopment
bypasses.

## Risks

| Risk | Mitigation |
|---|---|
| The Resolver lags, and the reconciler restores a row whose command is still in flight | A grace period of 60 min before any restore; the operation stays `OutcomeUnknown`; no automatic republish |
| An endpoint's subscriber has no inbox, so a duplicate command runs the handler twice | No automatic republish; retries with the same key return the existing operation; a person settles `OutcomeUnknown` |
| Action tokens fail across replicas | They use ASP.NET Data Protection, and no shared key ring is configured in code. App Service shares the key ring between instances; Container Apps does not. Document a single replica, or configure key persistence, for workloads. |
| The budget lags between replicas | The journal is the single count, and create-then-count refuses at the boundary |
| A stack trace leaks data into an issue | Off at both ends by default, frames only, scrubbed, never in other tools; the prompt forbids quoting payload values |
| Ownership data steers the agent to the wrong repository | P3.0 first; Owner-only edits, audited; https-only URLs; the prompt never targets the NimBus repository |

## Unchanged

§12 of the spec still holds, apart from the amendments in D1, D3 and D4: no hosting of agents, no
tracker or repository credentials in NimBus, no unattended skip, no payload edits by agents, no
issues against the NimBus repository, and no wake-on-failure. The Agents view and bus
participation over MCP stay "later" (§10).
