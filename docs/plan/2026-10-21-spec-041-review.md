Reviewer: Codex (codex-cli 0.163.0, read-only), 2026-10-21. Spec: [`docs/spec/041-on-prem-rabbitmq-transport/spec.md`](../spec/041-on-prem-rabbitmq-transport/spec.md) at `6ebc0d5f`. Each revision answers the findings before it; see the spec's §11.



**Checks run:** Read `AGENTS.md`, `CONTRIBUTING.md`, `docs/versioning.md`, and the full spec; checked `git status`, `git diff origin/master...HEAD`, and source and test references with `rg` and `Get-Content`; checked RabbitMQ’s official documentation. No build or tests were run because this was a read-only review. No files were changed.

## Code claims

1. **[blocking] Deferred replay is triggered on a separate subscription** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:185`) — §4.5 says `ProcessDeferredRequest` goes to the endpoint and is handled by the same hosted service. [ResponseService.cs](../../src/NimBus.Core/Messages/ResponseService.cs:377) addresses it to `DeferredProcessor`; [TopologyDescriptor.cs](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs:195) gives it a non-session subscription; and [DeferredMessageProcessorHostedService.cs](../../src/NimBus.SDK/Hosting/DeferredMessageProcessorHostedService.cs:80) consumes it separately. `StrictMessageHandler` explicitly does not handle the trigger ([line 431](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:431)). Specify a RabbitMQ trigger route and consumer, or explicitly change the dispatch contract.

2. **[should-fix] The §2.5 ordering gap is real, but the counter cannot serve as written as its guard** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:90`) — After unblock, [StrictMessageHandler.cs](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:99) checks `BlockedByEventId` only; [MessageHandler.cs](../../src/NimBus.Core/Messages/MessageHandler.cs:218) adds no replay guard. The trigger is processed separately, and [DeferredMessageProcessor.cs](../../src/NimBus.ServiceBus/DeferredMessageProcessor.cs:116) republishes parked messages to the main topic. A new message can therefore be handled first on Service Bus today. Existing tests cover replay and trigger registration, but I found no test for that overtaking window. Also, production code increments `DeferredCount` when parking ([StrictMessageHandler.cs:506](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:506)); searches found no production call to `DecrementDeferredCount` or `ResetDeferredCount`. Define a new, accurate pending-replay state before using `DeferredCount > 0` as §4.4 proposes.

3. **[should-fix] Transient abandon does not behave as described** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:61`) — Core calls `Abandon`, but Service Bus [MessageContext.cs](../../src/NimBus.ServiceBus/MessageContext.cs:257) implements it as a no-op. Its comment says the unsettled delivery returns after session release or lock expiry; the spec’s “redelivers … under the same session lock” is unsupported. Compare RabbitMQ retry behavior with that actual baseline.

4. **[should-fix] Failure completion and retry are conditional** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:45`) — The normal handler-failure path sends an error, blocks, completes, then checks for retry ([StrictMessageHandler.cs:153](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:153)). [CheckForRetry](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:647) can schedule nothing when no policy applies. A failed response, state write, or settlement also leaves the delivery unsettled. Qualify “the main queue never holds a failed message” and “schedule a retry” as normal-path behavior.

## Design

1. **[blocking] Forwarding loses more than `To`** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:130`) — Current forward rules stamp `From`, a **new `EventId` per fan-out copy**, and `To`; retry and continuation rules also stamp `From` and `To` ([TopologyDescriptor.cs](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs:94)). Reading the consumed queue restores only `To`. RabbitMQ exchange-to-exchange bindings route the original message; they do not republish or transform it ([RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges)). Specify stable, per-destination envelope creation, including `EventId` and `From`, before claiming equivalent Resolver and retry behavior.

2. **[blocking] The proposed replay guard has no completion protocol** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:173`) — Core calls “take sequence,” `ISender.Send`, then “increment count” as separate operations ([StrictMessageHandler.cs:506](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:506)); the spec promises one SQL transaction without explaining how those calls share it. It then parks every non-replay while `DeferredCount > 0`, but gives no atomic step that clears the guard after the final confirmed replay, including arrivals during a drain or a replay parked again. With the current counter behavior, this would park future traffic indefinitely. Define the transaction boundary, replay marker, count transitions, drain ownership, and empty-to-open transition.

3. **[blocking] `basic.nack` can retry forever on RabbitMQ 4.3+** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:202`) — The default limit of 20 is real, but RabbitMQ says explicit `nack` returns **do not increment** the delivery count from 4.3 onward. A transient failure can therefore occupy a partition indefinitely, contrary to the spec’s “up to the delivery limit” rationale and the parity table’s failure-isolation claim. Choose a bounded retry operation and policy; test it on a pinned server version. [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues).

4. **[blocking] Confirm-then-delete permits duplicate replay and scheduling** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:182`) — A crash after publisher confirmation but before deleting a parked or scheduled row republishes it. [DeferredMessageProcessor.cs](../../src/NimBus.ServiceBus/DeferredMessageProcessor.cs:190) currently gives replays fresh broker `MessageId`s, so merely keying SQL parking by the original `MessageId` does not make this replay idempotent. Publisher confirms and consumer acknowledgements are independent; RabbitMQ can also confirm an *unroutable* publish unless mandatory returns are handled ([RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms)). Specify stable replay/dispatch identity, destination-side deduplication, mandatory-return handling, and the exact SQL-commit-before-broker-ack sequence. The phase-2 crash tests should prove those rules.

5. **[should-fix] Lease epochs fence only part of the work** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:216`) — The proposed epoch covers `SessionState` and `ParkedMessage`, but an overlapping old handler can still publish a Resolver response, schedule a retry, or write inbox/outbox state before its broker ack fails. The spec also does not say how SQL atomically assigns a new epoch when RabbitMQ promotes a consumer. Narrow the §5 “state writes after lock loss rejected” claim and define epoch acquisition and the writes it fences.

6. **[should-fix] Partition routing and resizing are underspecified** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:140`) — A headers exchange ignores the routing key, so the “routing key or a header” choice requires a concrete topology ([RabbitMQ AMQP concepts](https://www.rabbitmq.com/tutorials/amqp-concepts)). More seriously, a producer computes one partition value, while §7 allows different `N` per destination: an exchange binding cannot recompute that value for each forwarded endpoint. Draining current queues before changing `N` also leaves scheduled sends, parked rows, retries, and outbox entries that can later use an old partition scheme. Define destination-specific routing and a versioned cutover for all pending sources.

7. **[should-fix] Session-less messages need an ingress rule** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:149`) — [Event.GetSessionId](../../src/NimBus.Abstractions/Events/Event.cs:23) generates a GUID for SDK events without a key, but [MessageHelper.cs](../../src/NimBus.ServiceBus/MessageHelper.cs:141) also accepts an `IMessage.SessionId` as supplied; the deferred dispatcher explicitly handles a missing ID ([DeferredMessageDispatcher.cs:74](../../src/NimBus.SDK/Hosting/DeferredMessageDispatcher.cs:74)). State whether RabbitMQ rejects, assigns, or accepts missing IDs at every ingress, and preserve the assigned value through retries and replies.

## Completeness and rules

1. **[blocking] The four Core contracts do not cover the public SDK surface** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:227`) — [ISubscriberClient](../../src/NimBus.SDK/ISubscriberClient.cs:8) inherits the Service Bus-specific `IServiceBusAdapter`; [PublisherClient.Request](../../src/NimBus.SDK/PublisherClient.cs:254) directly accepts a Service Bus reply session; and [OutboxDispatcherSender](../../src/NimBus.SDK/Hosting/OutboxDispatcherSender.cs:9) inherits a Service Bus sender. The phase-1 seam and phase-2 request/reply tests must cover receiving, reply receiving, handoff, and outbox dispatch. Keep existing public APIs with working `[Obsolete]` bridges as required by [docs/versioning.md](../../docs/versioning.md).

2. **[should-fix] “No Azure dependency at runtime” needs a wider WebApp and Resolver inventory** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:270`) — [Startup.cs](../../src/NimBus.WebApp/Startup.cs:31) unconditionally registers Service Bus clients and simulation; [Startup.Web.cs](../../src/NimBus.WebApp/Startup.Web.cs:139) registers a Service Bus heartbeat sender; [EndpointImplementation.cs](../../src/NimBus.WebApp/Controllers/ApiContract/EndpointImplementation.cs:38) requires Service Bus management; and [Resolver.Host/Program.cs](../../src/NimBus.Resolver.Host/Program.cs:44) constructs a Service Bus receiver. The `rg` inventory also finds Cosmos-specific WebApp controller and integration-intelligence paths. Capability flags alone do not make these compositions start without Azure configuration. Add a per-feature startup and API inventory, with on-prem behavior for each.

3. **[should-fix] The schedule and estimate precede required design decisions** (`docs/spec/041-on-prem-rabbitmq-transport/spec.md:297`) — The repo requires an issue and ADR discussion for transport and public-contract changes ([CONTRIBUTING.md](../../CONTRIBUTING.md)); phase 0 correctly acknowledges this. Yet phase 1 promises an in-memory and emulator conformance suite before the receiver, replay-trigger, reply-receiver, fencing, and crash guarantees are defined. The 2–3-week phase-2 estimate has no work breakdown for those seams or the SQL/RabbitMQ failure tests. Define acceptance semantics and split those deliverables before using the estimate for planning.

## Summary

**Code claims:** 4 findings, worst **blocking**. **Design:** 7 findings, worst **blocking**. **Completeness and rules:** 3 findings, worst **blocking**.

**Verdict: rethink.** Fixed partition queues with a single active consumer are a plausible ordering primitive, and the claimed Service Bus overtaking gap is real. The spec does not yet establish equivalent routing, bounded transient retries, or a replay and crash protocol that preserves messages and order.

## New findings by axis

### Core state and replay

- **[blocking] `ParkedBehindEventId` conflates backlog with block ownership.** During a drain, §4.5 makes `GetBlockedByEventId` return old blocker A to non-replay contexts even when the actual block is empty—or later belongs to B. `HandleEventRequest` treats a matching A as an already settled blocking delivery; `HandleRetryRequest` uses `IsSessionBlockedByThis` and the apparent blocker to decide whether to restart a drain; resubmission’s pending-handoff branch compares the apparent blocker before calling `BlockSession`. If `IsSessionBlockedByThis` uses A, a skip or handoff settlement for B is rejected; if it uses the real block, these paths disagree about session state. §4.5 leaves that decision to phase 2 rather than defining it ([spec:234](../spec/041-on-prem-rabbitmq-transport/spec.md:234), [StrictMessageHandler.cs:99](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:99), [StrictMessageHandler.cs:180](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:180), [StrictMessageHandler.cs:278](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:278), [StrictMessageHandler.cs:463](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:463)).

- **[blocking] A redelivered skip can strand its parked rows.** For a skip of actual blocker A, Core unblocks and *then* publishes the drain trigger. If it stops between those calls, the redelivered skip fails `VerifySessionIsBlockedByThis`; its catch sends only `SkipResponse` and completes. No trigger remains to drain the parked rows. Handoff completion has an explicit repair branch; skip does not ([StrictMessageHandler.cs:326](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:326), [StrictMessageHandler.cs:348](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:348), [spec:262](../spec/041-on-prem-rabbitmq-transport/spec.md:262)).

- **[blocking] “Inbox recognises a successful replay” does not make that replay harmless.** If a handler succeeded and its inbox record committed but the parked row remains, the next replay’s pre-check sends a *SkipResponse*. SQL treats terminal writes as unguarded, so that response can replace the prior **Completed** state with **Skipped**. Preserving `MessageId` prevents rerunning the handler but does not preserve the Resolver result ([spec:249](../spec/041-on-prem-rabbitmq-transport/spec.md:249), [StrictMessageHandler.cs:90](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:90), [ResponseService.cs:37](../../src/NimBus.Core/Messages/ResponseService.cs:37), [SqlServerMessageTrackingStore.Writes.cs:169](../../src/NimBus.MessageStore.SqlServer/SqlServerMessageTrackingStore.Writes.cs:169)).

- **[should-fix] The proposed parked identity is not the object Core sends.** `SendToDeferredSubscription` creates a new `Message` without `MessageId`; it carries the source ID in `InboxMessageId` and `ParentMessageId`. §4.5 says `ISender.Send` inserts a row unique on `MessageId` and replays with the original ID, but never defines the translation. The insert must explicitly take the source identity, or the uniqueness and replay claims fail ([ResponseService.cs:313](../../src/NimBus.Core/Messages/ResponseService.cs:313), [spec:211](../spec/041-on-prem-rabbitmq-transport/spec.md:211), [spec:224](../spec/041-on-prem-rabbitmq-transport/spec.md:224)).

- **[should-fix] “Normal pipeline” needs an explicit replay settlement result.** `MessageHandler.Handle` catches blocked and handler-failure exceptions and returns; a completed task does not mean the replay succeeded. Core also calls `Complete` on both successful events and handled failures, and calls it after parking. The replay consumer needs defined outcomes for deleting a row, retaining it, and stopping the batch, plus a transaction boundary compatible with inbox recording and Core’s earlier state calls ([MessageHandler.cs:37](../../src/NimBus.Core/Messages/MessageHandler.cs:37), [StrictMessageHandler.cs:146](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:146), [StrictMessageHandler.cs:506](../../src/NimBus.Core/Messages/StrictMessageHandler.cs:506), [spec:248](../spec/041-on-prem-rabbitmq-transport/spec.md:248)).

### Routing and identity

- **[blocking] Sender-side fan-out does not cover all ingress and dispatch paths.** The outbox dispatcher publishes through its own `ISender`; Manager currently publishes directly; WebApp and other raw Service Bus paths need inventory. The external PartnerPortal publishes a raw CloudEvent without any NimBus sender, while CloudEventsInterop also has a raw *consumer* that expects the original publication. The routing table cannot fan out traffic that bypasses its sender, and §9 tests only the sender path ([spec:152](../spec/041-on-prem-rabbitmq-transport/spec.md:152), [OutboxDispatcher.cs:206](../../src/NimBus.Core/Outbox/OutboxDispatcher.cs:206), [ManagerClient.cs:66](../../src/NimBus.Manager/ManagerClient.cs:66), [PartnerPortal/Program.cs:115](../../samples/CrmErpDemo/PartnerPortal/Program.cs:115), [CloudEventsInterop.NonNimBusConsumer/Program.cs:4](../../samples/CloudEventsInterop/CloudEventsInterop.NonNimBusConsumer/Program.cs:4)).

- **[blocking] The deterministic `EventId` seed is normally absent.** `PublisherClient.GetMessageStatic` sets `MessageId` but not `EventId`; the Service Bus forward action generates the latter. UUIDv5 of “original `EventId` and consumer” therefore has no usable original for ordinary SDK publishes, and raw CloudEvents have none either. Define an identity from stable populated fields, including producer and logical message identity, and test repeat publishes and multiple producers ([spec:156](../spec/041-on-prem-rabbitmq-transport/spec.md:156), [PublisherClient.cs:431](../../src/NimBus.SDK/PublisherClient.cs:431), [TopologyDescriptor.cs:104](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs:104)).

### Broker, fencing, and acceptance

- **[should-fix] First-delivery lease acquisition does not reject every post-loss write claimed in §5.** After the old consumer loses its connection, its epoch remains current until the successor receives a message and increments it. Old handler SQL writes in that interval pass. The epoch check must also be part of each write’s SQL transaction; a separate check can race promotion. The phase 2 overlap test starts only after takeover and misses this window ([spec:312](../spec/041-on-prem-rabbitmq-transport/spec.md:312), [spec:362](../spec/041-on-prem-rabbitmq-transport/spec.md:362), [spec:417](../spec/041-on-prem-rabbitmq-transport/spec.md:417)). RabbitMQ documents active-consumer notifications for AMQP 1.0, [not AMQP 0-9-1](https://www.rabbitmq.com/docs/consumers).

- **[should-fix] The request/reply queue must exist before publishing.** §4.9 says each client instance declares an exclusive, auto-delete queue but gives no order. Current `Request` sends first and only then starts receiving; with a new RabbitMQ reply queue, a fast response can be unroutable before declaration. Specify declaration and consumer setup before send, and test that race ([spec:323](../spec/041-on-prem-rabbitmq-transport/spec.md:323), [PublisherClient.cs:265](../../src/NimBus.SDK/PublisherClient.cs:265)).

- **[should-fix] §5 and §9 overstate what is established.** “New message overtakes parked ones: No” depends on the unresolved Core paths; “state writes after lock loss rejected” depends on a successor’s first delivery. The crash tests need skip-after-unblock, inbox-record-before-row-delete, old-blocker retry/resubmission during drain, and new blocker B while A’s rows remain. Routing tests need outbox and external ingress, not only SDK fan-out ([spec:352](../spec/041-on-prem-rabbitmq-transport/spec.md:352), [spec:407](../spec/041-on-prem-rabbitmq-transport/spec.md:407)). The `basic.reject` limit and mandatory-return claims themselves match [RabbitMQ’s quorum-queue](https://www.rabbitmq.com/docs/quorum-queues) and [confirm](https://www.rabbitmq.com/docs/confirms) documentation.

## Summary

**Verdict: rethink.** The broker topology and bounded transient retry are substantially clearer. The synthetic blocker, in-partition replay contract, and sender-only routing still fail concrete Core paths. Define those state and ingress contracts before using §5 parity or §9 as phase 2 exit criteria. This was a read-only source and RabbitMQ-documentation review at `b338286d`; no files changed and no tests ran.

### New findings

1. **[blocking] Define the forwarder from the complete subscription matrix.** `TopologyDescriptor` has endpoint, reply, Resolver fan-out, Deferred, DeferredProcessor, compiled forward and dynamic forward subscriptions. In particular, the Resolver fan-out takes both `To=Resolver` (stamping `From=E`) **and** `To=E`; the Resolver topic then accepts all forwarded messages through its retained `$Default` rule. §4.1 describes event copies and a broad “addressed to an endpoint” case, but does not specify those separate copies and filters. A direct reply queue in §4.9 can replace the reply subscription, but must be identified as that replacement rather than an unspecified forwarder rule ([TopologyDescriptor.cs:123](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L123), [TopologyDescriptor.cs:146](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L146), [TopologyDescriptor.cs:161](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L161), [TopologyDescriptor.cs:179](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L179), [TopologyDescriptor.cs:345](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L345), [spec §4.1](../spec/041-on-prem-rabbitmq-transport/spec.md#41-topology-and-the-forwarder)).

2. **[blocking] Spell out `To`/`From` per control route.** The current rules pass `To=E` unchanged; redirect `To=Retry` or `To=Continuation` to E and stamp `From=Retry` or `From=Continuation`; stamp `From=E` on a `To=Resolver` audit copy; select Deferred only when `OriginalSessionId` is present; and send `To=DeferredProcessor` to its separate consumer. These are different actions on different subscription copies. §4.1’s single addressed-message rule cannot be implemented unambiguously, especially when several rules match one publication ([TopologyDescriptor.cs:130](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L130), [TopologyDescriptor.cs:168](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L168), [TopologyDescriptor.cs:186](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L186), [ResponseService.cs:377](../../src/NimBus.Core/Messages/ResponseService.cs#L377)).

3. **[blocking] The two intake lanes can reverse a session’s order.** A raw publication and an SDK publication for the same session enter `raw` and `p<i>` queues with independent active forwarders; either can reach the destination partition first. Prefetch 1 preserves order *within one intake queue*, not across those queues or a direct replay/scheduled publish to the destination. §5’s per-session-order row therefore needs a scope or a unified ingress ordering rule, and §9 needs a mixed raw/SDK same-session test ([spec §§4.1–4.2](../spec/041-on-prem-rabbitmq-transport/spec.md#41-topology-and-the-forwarder), [RabbitMQ broker semantics](https://www.rabbitmq.com/docs/semantics)).

4. **[should-fix] The `EventId` seed omits identity needed for distinct copies.** CloudEvents guarantees uniqueness for **`source` plus `id`**, not `id` alone. Also, compiled and dynamic subscriptions can both target C for an event; Service Bus creates separate rule-action copies, while UUIDv5 of publish-id and C gives them the same `EventId`. Include producer/source and subscription or rule identity in the stable seed, and state how the original `MessageId` survives forwarding for inbox deduplication ([spec §4.1](../spec/041-on-prem-rabbitmq-transport/spec.md#41-topology-and-the-forwarder), [TopologyDescriptor.cs:307](../../src/NimBus.ServiceBus/Provisioning/TopologyDescriptor.cs#L307), [CloudEvents specification](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md), [InboxDuplicateDetector.cs](../../src/NimBus.Core/Inbox/InboxDuplicateDetector.cs)).

5. **[blocking] “Ack after every copy is confirmed” can still lose a route.** §4.1 does not require `mandatory` plus return handling for each forwarder publish. RabbitMQ confirms an unroutable publication too; the intake could then be acknowledged without a destination copy. If an earlier copy was confirmed and a later one fails, intake redelivery also republishes the earlier copy: stable `EventId` makes its identity repeatable but is not broker deduplication. Specify return handling and destination duplicate behavior ([spec §4.1](../spec/041-on-prem-rabbitmq-transport/spec.md#41-topology-and-the-forwarder), [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms)).

6. **[should-fix] The alternate exchange does not make arbitrary-key originals visible to raw consumers.** An alternate exchange is an **exchange**, so its type and bindings need defining. As written, an unknown routing key reaches the raw intake through the alternate exchange, while raw consumers bound on the direct exchange only to `p0…pN` and `raw` miss that original. Bind raw consumers to the alternate exchange too, and test an arbitrary key. RabbitMQ treats a message routed through the alternate exchange as routable even with `mandatory` ([spec §4.1](../spec/041-on-prem-rabbitmq-transport/spec.md#41-topology-and-the-forwarder), [RabbitMQ alternate exchanges](https://www.rabbitmq.com/docs/ae)).

7. **[should-fix] Lease loss needs an active-handler and settlement rule.** Holding the successor’s first delivery unacknowledged for a 60-second lease is below RabbitMQ’s default 30-minute timeout; it is not inherently a timeout failure. A configured shorter timeout or prolonged SQL outage can cancel its AMQP 0-9-1 consumer and requeue that delivery. More importantly, after renewal fails, §4.4 fences SQL writes but does not say to cancel the handler, suppress broker ack/publish, and release its delivery; those operations are outside the SQL predicate. Set a timeout margin and define this shutdown path ([spec §4.4](../spec/041-on-prem-rabbitmq-transport/spec.md#44-partition-lease), [RabbitMQ consumer timeouts](https://www.rabbitmq.com/docs/consumers), [quorum-queue timeout behavior](https://www.rabbitmq.com/docs/quorum-queues)).

8. **[should-fix] Specify the drain lock’s lifetime and observation loop.** A SQL application lock can serialize competing drainers if held across the full publish/confirm/delete loop. It does not lock the endpoint handler’s concurrent insertion of a newly parked replay. The Service Bus drain detects that insertion by receiving the new parked copy and comparing `ParentMessageId`; a one-time SQL row snapshot cannot do so. §4.6 needs a lock owner/lifetime, repeat reads and a defined empty-to-finish condition ([spec §4.6](../spec/041-on-prem-rabbitmq-transport/spec.md#46-parking-and-replay), [DeferredMessageProcessor.cs:83](../../src/NimBus.ServiceBus/DeferredMessageProcessor.cs#L83)).

9. **[should-fix] Qualify “Core is unchanged” with the required contract behavior.** The Core interfaces can remain, but the adapter must preserve `IMessageContext` settlement and session-state semantics; `IDeferredMessageProcessor.ProcessDeferredMessagesAsync` still takes `topicName` as the endpoint address; and `ScheduleRedelivery` must preserve the original `MessageId` and complete the original only after durable scheduling. §4.7 says only that it uses the scheduled table. The *existing hosted service* cannot consume a RabbitMQ trigger unchanged because it constructs a `ServiceBusProcessor` ([IMessageContext.cs:90](../../src/NimBus.Core/Messages/IMessageContext.cs#L90), [IDeferredMessageProcessor.cs:22](../../src/NimBus.Core/Messages/IDeferredMessageProcessor.cs#L22), [MessageContext.cs:594](../../src/NimBus.ServiceBus/MessageContext.cs#L594), [DeferredMessageProcessorHostedService.cs:72](../../src/NimBus.SDK/Hosting/DeferredMessageProcessorHostedService.cs#L72)).
