**Verdict: needs rework.** The 2026-10-05 revision addresses the prior review, but the cutover guard and background purge still permit concrete data-loss scenarios. I reviewed the current `7403c596` tree (`v4.6.0+1`). No files were changed; tests were not run for this document review.

## Blocking

1. **§5.5 — A live purge can delete new work.** The spec allows an endpoint purge to run for minutes or hours, calls overlap across WebApp instances “harmless,” and runs `ClearEndpoint` afterward (`spec.md:319-339`). `ClearEndpoint` deletes and recreates the endpoint’s Service Bus subscription (`src/NimBus.Management.ServiceBus/EndpointManagement.cs:18-27`). **Scenario:** messages arrive during the row scan; the scan can delete their new tracking rows, and the later subscription deletion discards messages received during the purge. Two instances can also clear the subscription while the other is still deleting. **Correction:** define a shared exclusion and quiescence protocol for the endpoint, including in-flight writes, and specify what happens to messages arriving after purge starts. Do not run `ClearEndpoint` after a failed row purge.

2. **§6.1, §6.5 — `MAX(_ts)` is not a safe migration guard.** The guard calls a layout ready when the current maximum does not exceed `sourceMaxTs`, then stops checking for the process lifetime (`spec.md:794-814`). The migration also treats *any* change in the maximum as evidence of a writer (`spec.md:615-617`). **Scenario:** after rollback, v4 deletes or purges a legacy row; the maximum stays equal or falls, so a later v5 process accepts a stale target row as ready. Conversely, TTL expiry of the row with the maximum can lower it during an otherwise quiet copy and fail migration. **Correction:** make rollback write fencing or marker reset enforceable, and use a reconciliation check that detects removals. Do not present a maximum timestamp as a complete backstop or cache ready indefinitely while legacy writers can exist.

3. **§6.1, §5.8, §6.5 — `--exclude` can authorize missing data and its deletion.** `--exclude <id>` records any selected container in `excluded` (`spec.md:525,564-565`); an excluded container satisfies Ready (`spec.md:798-800`) and becomes deletable in Admin → Storage containers (`spec.md:435-441`). The marker’s excluded entries also lack the `sourceMaxTs` required by Ready’s “no listed container” check (`spec.md:789-790`). **Scenario:** an operator excludes a catalog endpoint with Failed rows. V5 shows no rows for it, its sessions remain blocked, and the page permits deletion of the only legacy copy. **Correction:** reject exclusion of a nonempty active catalog endpoint, keep excluded sources protected, and define separate guard semantics for verified orphans.

4. **§6.1 — Same-second changes defeat rerun convergence.** A 409 replaces a copied row only if the source `_ts` is newer (`spec.md:597-605`), while verification is organized by `(status, deleted)` (`spec.md:618-626`). Cosmos `_ts` is a Unix **seconds** timestamp ([Microsoft date documentation](https://learn.microsoft.com/en-us/cosmos-db/query/dates)). **Scenario:** a source row is changed twice within one second after an initial copy, with its status unchanged. A rerun sees an equal `_ts`, retains old content, and the stated per-status verification can pass. **Correction:** stamp and compare the source version or content, such as its ETag plus a verified digest; define a conflict rule for unstamped v5 rows with equal timestamps.

5. **§6.2, §6.5 — The deploy preflight runs after a step that can resume the Resolver.** The runbook itself says `nb infra apply` rewrites app settings and can clear `AzureWebJobs.Resolver.Disabled` (`spec.md:658-668`). The GitHub workflow runs `infra apply` before `deploy apps` (`.github/workflows/deploy.yml:142,176`); the Azure Pipelines path runs `setup` (`pipelines/azure-pipelines-deploy.yml:156`). The proposed guard is in `deploy apps` and `setup` before *app deployment* (`spec.md:827-832`). **Scenario:** a routine pipeline starts during pending migration, re-enables the Resolver, then refuses app deployment. The Resolver consumes its ten-attempt store-failure budget and dead-letters messages (`src/NimBus.Resolver/Services/ResolverService.cs:205-246`). **Correction:** gate before infrastructure changes and preserve an explicitly disabled trigger throughout cutover.

## Should-fix

6. **§5.9 versus §6.5 — The public adapter surface cannot perform the guard as specified.** The spec lists only a LINQ iterator and throughput-create overload as interface additions (`spec.md:486-491`), but `TrackingLayout` must list containers and inspect their partition-key definitions (`spec.md:794-805`). `ICosmosDatabaseAdapter` has no container-list operation, and `ICosmosContainerAdapter` has no container-properties read (`src/NimBus.MessageStore.CosmosDb/CosmosAbstractions.cs:31-84`). `CosmosDbClient` also accepts an `ICosmosClientAdapter` without a raw SDK client (`CosmosDbClient.cs:109-129`). **Scenario:** an adapter-backed host cannot run the promised first-use guard. **Correction:** specify metadata/list operations with fail-closed adapter defaults and tests, or an explicit injected metadata interface covering both constructors.

7. **§5.4, §8, §9 — The current code has moved past the stated baseline.** The spec and ADR still say SQL Server and in-memory prefix-match `EventFilter.EndPointId` and require a future prerequisite (`spec.md:275-289`; `adr/017-single-cosmos-tracking-container.md:82-85`). They now match exactly (`src/NimBus.MessageStore.SqlServer/SqlServerMessageTrackingStore.Search.cs:160`; `src/NimBus.Testing/Conformance/InMemoryMessageStore.cs:308`). Conversely, the §5.4 operation table omits `TryArchiveUnresolvedEvent` and `TryRestoreArchivedEvent`, added at `IMessageTrackingStore.cs:105,115` and implemented with conditional read/replace at `CosmosDbMessageTrackingStore.Writes.cs:70-105`. The new operator coordinator calls them (`src/NimBus.WebApp/Services/Operations/OperatorCommandCoordinator.cs:351,391`). **Scenario:** implementation based on the table leaves those operations on legacy container access or fails them under the new scope. **Correction:** mark the exact-filter prerequisite complete; add both operations, their stamp-clearing behavior, isolation tests, and pending-layout behavior for operator tools.

8. **§5.5 — Audit entries cannot serve as the sole purge outcome.** The spec returns `202` without an operation identifier and promises that the outcome appears in the audit log (`spec.md:329-347`). `LogAuditAsync` may skip an enabled-off audit type and swallows durable-store write failures (`src/NimBus.WebApp/Services/AuditLogService.cs:46-80`). **Scenario:** a purge fails halfway after its `202`, but neither a start nor an outcome is available in the audit UI; falling counts do not show whether it finished. **Correction:** specify durable job status and an operation ID/status read, or use a required audit path with an explicit failure policy.

9. **§6.5 — Key-only deployment preflight conflicts with planned keyless accounts.** The spec fetches account keys for `nb deploy apps` and `nb setup` (`spec.md:827-831`), while Spec 034 plans Cosmos `disableLocalAuth` (`docs/spec/034-private-networking/spec.md:448-471`). The CLI already supports Cosmos endpoint URI plus Entra credentials (`src/NimBus.CommandLine/CommandRunner.cs:42-64`). **Scenario:** a keyless private deployment cannot pass the layout preflight without using the bypass flag. **Correction:** support Entra data-plane authentication from the in-network runner and include Cosmos connectivity in the private preflight.

10. **§6.4 — The autoscale restore limit omits storage.** The spec says the lowest later maximum is the historical highest maximum divided by ten (`spec.md:767-773`). Microsoft’s rule is the maximum of **1,000, historical maximum ÷ 10, and current GB × 10**, rounded to 1,000 ([autoscale FAQ](https://learn.microsoft.com/en-us/azure/cosmos-db/autoscale-faq)). **Scenario:** once `unresolvedevents` exceeds 400 GB, runbook step 8 cannot restore a 4,000 RU/s maximum even if the migration never raised it above 10,000. **Correction:** use the full formula in sizing and the restore step.

11. **§5.8, §9 — Retiring a page and API route in a 5.x minor conflicts with repository versioning.** The decision removes both in a later minor (`spec.md:447-453,1148`), while `docs/versioning.md:4-10` classifies observable behavior removal as major and places deprecation in a minor. **Scenario:** an existing client of `/api/admin/storage/cosmos/containers` breaks on a minor upgrade. **Correction:** keep and deprecate the route in 5.x, remove it in v6, or record an explicit policy exception. Also update `CosmosContainerDefaultsTests.cs:18,53` when marking its called methods `[Obsolete]`: compiler warnings fail Release (`Directory.Build.props:49`).

The API schema still says “per-endpoint storage container” (`src/NimBus.WebApp/api-spec.yaml:3901-3904`), and the Admin UI says “Delete the entire endpoint container” (`src/NimBus.WebApp/ClientApp/src/components/admin/advanced-operations.tsx:563`). **Correction:** refresh references and the schema/UI wording as part of Phase 1.

13. **§6.1 — Recheck the emulator bulk claim.** The spec says the vNext emulator does not support .NET bulk (`spec.md:637-638`), while the current [Microsoft vNext feature table](https://learn.microsoft.com/en-us/azure/cosmos-db/emulator-linux) lists Bulk API as supported. **Unverified for the pinned dated image:** the documentation does not establish what `vnext-EN20260907` supports. **Correction:** test that exact image and qualify the statement; bounded parallel creates may still be the preferred design.

## Claims verified as accurate

- The current store still has **13** `GetItemQueryIterator<T>` sites against endpoint containers; the additional sites query `messages`, `audits`, or `eventreports`.
- The 13 reserved IDs and the 3.62.1 Cosmos SDK pin match the current tree (`CosmosContainerDefaults.cs:31-39`; `NimBus.MessageStore.CosmosDb.csproj:18`).
- Microsoft documents `MultiHash` prefix routing and `/id` as a suitable last key level ([hierarchical keys](https://learn.microsoft.com/en-us/azure/cosmos-db/hierarchical-partition-keys)); the 10,000 RU/s physical-partition ceiling and autoscale range are documented ([autoscale FAQ](https://learn.microsoft.com/en-us/azure/cosmos-db/autoscale-faq)).
- Priority-based execution is best effort; Data Explorer defaults to Low when enabled, and a Low request is ignored when the account feature is disabled ([priority documentation](https://learn.microsoft.com/en-us/azure/cosmos-db/priority-based-execution), [SDK request option](https://learn.microsoft.com/en-us/dotnet/api/microsoft.azure.cosmos.requestoptions.prioritylevel)). Delete by partition key remains preview and requires a full hierarchical key ([Microsoft documentation](https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/how-to-delete-by-partition-key)). Azure documents an App Service request timeout of about 230 seconds on Windows and 240 seconds on Linux ([Microsoft documentation](https://learn.microsoft.com/en-us/troubleshoot/azure/app-service/web-request-times-out-app-service)).
